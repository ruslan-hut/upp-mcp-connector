# MCP Connector для УПП 1.3

Слой интеграции **Model Context Protocol** для конфигурации «Управление производственным
предприятием для Украины, ред. 1.3». Открывает данные учётной системы LLM-клиентам
(Claude и другим) — через HTTP-сервис в 1С и внешний шлюз.

Это **не конфигурация**, а только подсистема `MCPConnector`: восемь объектов метаданных,
выгруженных в иерархический файловый формат. Типовая УПП сюда не входит и не может входить —
это лицензионный продукт вендора.

## Что внутри

| Объект | Назначение |
|---|---|
| `HTTPServices/MCP` | Единственная точка входа. Аутентификация по ключу, проверка скоупов, маршрутизация |
| `CommonModules/MCP` | Резолверы и отчёты — вся бизнес-логика |
| `CommonModules/MCP_JSON` | Упаковка/распаковка JSON, разбор дат |
| `CommonModules/MCP_Утилиты` | Приведение типов, экранирование `ПОДОБНО`, логирование |
| `Catalogs/MCP_УчетныеЗаписи` | Ключи доступа: сотрудник, ключ, активность, скоуп, организация |
| `Enums/MCP_Скоупы` | Права: resolve, отчёты по остаткам / продажам / деньгам / себестоимости, журнал |
| `Subsystems/MCPConnector` | Группировка перечисленного |

Роли в выгрузке нет — её нужно создать при внедрении, состав описан ниже. Ссылка на роль
убрана и из состава подсистемы, так что выгрузка импортируется как есть.

## Контракт

```
GET  /mcp/health
POST /mcp/auth/verify
POST /mcp/resolve/{entity}     customer | product | material | warehouse | firm
                               cash | operation | cost_article
POST /mcp/reports/{type}       stock | sales | top_products | customer_summary
                               cash_balance | cash_flow | receivables | payables
                               specification | specification_cost | specification_explode
                               specification_where_used | specification_versions
                               specification_list | production_output
                               production_consumption | production_document
POST /mcp/admin/{action}
```

Отчёт отвечает структурой `{columns, rows, totals}`. `columns[].type` — `ref | number |
string | date`. Ссылочная ячейка приходит объектом `{id, label}`, чтобы читателю не
приходилось на каждую строку звать резолвер; составная аналитика добавляет `kind`.

Скоупы приходят заголовком `X-MCP-Scopes`, идентификатор учётной записи — `X-MCP-Sub`.
HTTP-слой кладёт в параметры отчёта доверенные ключи `_sub` и `_allow_cost`, которым
тело запроса управлять не может.

### Отбор либо применяется, либо отклоняется

Принцип, на котором держится доверие к цифрам: **фильтр нельзя проигнорировать молча**.
Если база не может поддержать отбор — отчёт отвечает 400 с объяснением, а не отдаёт
невыборку под видом выборки. Отказ стоит одной повторной попытки; тихо пропущенный
фильтр — это неверный ответ, который выглядит правильным.

Из того же соображения: если переданы идентификаторы, но ни один не резолвится — это
ошибка, а не «отбор без условий». Иначе опечатка в UUID вернула бы честный ноль, который
прочитали бы как «товара нет на складе».

Каждый отчёт отдаёт `applied_filters` — по нему видно, что выборка действительно сужена.

## Источники данных

Выбор регистров — решение под конкретную базу, а не универсальный рецепт. Здесь он такой:

| Отчёт | Регистр | Почему |
|---|---|---|
| `stock` | `ТоварыНаСкладах` + `ПартииТоваровНаСкладах` + `ТоварыВРезервеНаСкладах` | Управленческий контур: в регламентированном учёт ведётся без разреза складов, а склад — основная группировка. Стоимость — из партий, резерв даёт `available = qty − reserved` |
| `sales` | `Продажи` + `ПродажиСебестоимость` | Выручка = `Стоимость − НДС`: ресурс хранится с налогом, и только без него сумма сопоставима с себестоимостью. Себестоимость связывается по регистратору |
| `cash_balance` / `cash_flow` | `ДенежныеСредства`, `ДвиженияДенежныхСредств` | Суммы из `СуммаУпр`: `Сумма` хранится в валюте счёта, складывать разные валюты нельзя |
| `receivables` / `payables` | `ВзаиморасчетыСКонтрагентами` | Развёрнутое сальдо по ключу регистра. Роль — из вида договора; бартер и прочее — по знаку сальдо |
| `specification*` | `СпецификацииНоменклатуры` | Состав — ТЧ `ИсходныеКомплектующие` активной спецификации. Товар спецификации задаётся её ТЧ `ВыходныеИзделия`, а не реквизитом шапки; норма считается на выпуск в N единиц, а не на одну |
| `production_output` | `ВыпускПродукции` | Обороты выпуска. Регистр вместо ТЧ документа: он уже свёрнут и не зависит от того, каким документом оформлена операция |
| `production_consumption` | `ЗатратыНаВыпускПродукции` | Расход материалов с привязкой к продукции. Измерение `Затрата` составное, материалом считается только ссылка на номенклатуру |
| `purchases` | `Закупки` | Обороты закупок, возвраты поставщикам уже учтены знаком. Склада, валюты документа и признака «в пути» в регистре нет — эти разрезы отклоняются |
| `returns` | ТЧ `ВозвратТоваровОтПокупателя` + отрицательные строки `ОтчетОРозничныхПродажах` | Не регистр: в `Продажи` возврат сворачивается с продажей и теряет построчный склад, в партиях нет покупателя и суммы возврата. Розничные возвраты отличаются префиксом номера узла обмена с Розницей (`00РТ`) |

Склад и продавец в регистре продаж отсутствуют — извлекаются из документа-регистратора
через `ВЫРАЗИТЬ`. Склад есть в шапке только у реализации и отчёта о розничных продажах;
у возврата — лишь составной `СкладОрдер`.

## Установка

1. Объединить конфигурацию с этой выгрузкой в Конфигураторе. Нужны типовые объекты УПП:
   подсистема ссылается на `Справочник.Пользователи`, `Справочник.Организации`,
   `Справочник.Номенклатура`, `Справочник.Контрагенты`, `Справочник.Склады` и регистры
   из таблицы выше — сама по себе выгрузка не самодостаточна.
2. Создать роль (например `MCP_Сервис`) по составу из раздела ниже и включить её
   в состав подсистемы `MCPConnector`.
3. Опубликовать HTTP-сервис `MCP`.
4. Завести элемент `MCP_УчетныеЗаписи`: сотрудник, ключ доступа, скоуп, активность.
5. Обработчики формы элемента лежат в `docs/` отдельным сниппетом: обычные формы
   выгружаются в двоичный `Form.bin`, и код модуля формы из выгрузки нечитаем.
6. Настроить внешний шлюз на адрес публикации.

## Роль

Роль не выкладывается: в реальном внедрении она перечисляет объекты конкретной базы,
включая доработки, которых у вас не будет. Состав ниже — минимум, при котором работают
все реализованные отчёты; он выведен из кода модулей, а не переписан с боевой роли.

Пользователь, под которым выполняется HTTP-сервис, должен иметь **только эту роль** —
сервис отдаёт данные наружу, и лишние права здесь превращаются в лишние данные в ответе.

**Права конфигурации:** `ThinClient`, `WebClient`, `MainWindowModeNormal`, `SaveUserData`,
`Output`. Для админ-инструментов дополнительно `ActiveUsers` и `EventLog`.

**HTTP-сервис** `MCP` — право `Use` на методы всех шаблонов URL: `Health.Get`,
`AuthVerify.Post`, `Resolve.Post`, `Reports.Post`, `Admin.Post`.

**Чтение справочников (23):** `MCP_УчетныеЗаписи`, `Номенклатура`, `Склады`, `Качество`,
`Контрагенты`, `ДоговорыКонтрагентов`, `Организации`, `Менеджеры`, `Пользователи`,
`ФизическиеЛица`, `Кассы`, `БанковскиеСчета`, `КассыККМ`, `Валюты`,
`СтатьиДвиженияДенежныхСредств`, `СтатьиЗатрат`, `СпецификацииНоменклатуры`,
`НоменклатурныеГруппы`, `Подразделения`, `ТипыЦенНоменклатуры`, `Проекты`,
`ПричиныВозвратаТоваров`, `ЕдиницыИзмерения`.

**Чтение регистров накопления (11):** `ТоварыНаСкладах`, `ПартииТоваровНаСкладах`,
`ТоварыВРезервеНаСкладах`, `Продажи`, `ПродажиСебестоимость`, `ДенежныеСредства`,
`ДвиженияДенежныхСредств`, `ВзаиморасчетыСКонтрагентами`, `ВыпускПродукции`,
`ЗатратыНаВыпускПродукции`, `Закупки`.

**Чтение регистра сведений:** `ЦеныНоменклатуры`.

**Чтение документов (8)** — из них отчёт продаж достаёт склад и продавца, которых нет
в регистре, карточка производства — табличные части, а отчёт возвратов читает строки
возвратов и отчётов о розничных продажах: `РеализацияТоваровУслуг`,
`ОтчетОРозничныхПродажах`, `ВозвратТоваровОтПокупателя`, `ОтчетКомиссионераОПродажах`,
`ОтчетКомитентуОПродажах`, `АктОбОказанииПроизводственныхУслуг`,
`РеализацияУслугПоПереработке`, `ОтчетПроизводстваЗаСмену`.

Перечислениям права в 1С не назначаются — `MCP_Скоупы`, `ВидыДоговоровКонтрагентов`
и `ВидыДвиженийПриходРасход` читаются без отдельного разрешения.

Права на запись не нужны нигде: интеграция только читает. Единственное исключение —
справочник учётных записей, который ведёт администратор вручную под своей ролью.

## Шлюз

Между LLM-клиентом и 1С стоит отдельный Go-сервис: он держит MCP-протокол, схемы
инструментов, OAuth и мультибазовость, а тело запроса и ответа передаёт как есть.
В этот репозиторий он не входит.

## Платформа

- BSL, `ScriptVariant = Russian` — ключевые слова и идентификаторы русские.
- Обычные формы, `DefaultRunMode = OrdinaryApplication`.
- `CompatibilityMode = Version8_2_13`: недоступны `СтрСоединить`, `СтрНайти` и часть
  современных API. В модулях есть собственные `Соединить()` и `РазделитьСтроку()` —
  это не изобретение велосипеда, а следствие режима совместимости.
- Кириллические пути: работать с репозиторием через `git -c core.quotepath=false`.
